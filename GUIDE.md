# Подробный разбор проекта «Кредитный скоринг»

Этот файл — для понимания: что и зачем сделано на каждом шаге, какая теория стоит за решениями,
как читать результаты и что по этой теме спрашивают на собеседованиях.

## 1. Постановка задачи

Банк выдаёт кредитную карту и хочет оценить **PD (probability of default)** — вероятность того, что клиент
не внесёт платёж в следующем месяце. По PD банк решает, одобрять ли заявку, и какой лимит ставить.

Это **бинарная классификация**, но важны не столько метки «да/нет», сколько:
- **ранжирование** клиентов по риску (кому отказать в первую очередь) — его меряет ROC-AUC / Gini;
- **калиброванность** вероятностей (PD = 0,1 должен означать, что дефолтит каждый десятый) — от PD считают
  ожидаемые потери EL = PD · LGD · EAD и резервы.

### Данные

UCI *Default of Credit Card Clients*: 30 000 клиентов, апрель–сентябрь 2005 года.

| признаки | что значат |
|---|---|
| `LIMIT_BAL` | кредитный лимит |
| `SEX`, `EDUCATION`, `MARRIAGE`, `AGE` | демография |
| `PAY_1..PAY_6` | статус платежа по месяцам: −2 — не пользовался картой, −1 — погасил полностью, 0 — внёс минимальный платёж (револьверный кредит), k ≥ 1 — просрочка k месяцев. Индекс 1 — сентябрь (последний месяц) |
| `BILL_AMT1..6` | сумма выставленного счёта |
| `PAY_AMT1..6` | сумма внесённого платежа |

**Подвохи данных** (их стоит заметить сам, это любят спрашивать):
- в `EDUCATION` встречаются коды 0, 5, 6, которых нет в документации, в `MARRIAGE` — код 0. Мы сводим их к «другое»;
- в `PAY_2..PAY_6` почти нет значения 1 (у `PAY_6` — ни одного): видимо, кодировка месяцев различалась;
- `BILL_AMT` бывает отрицательным — переплата;
- 35 полностью одинаковых строк.

## 2. Протокол эксперимента — почему так

1. **Отложенный test (20%)** откладывается сразу и до конца не трогается. На нём только итоговые цифры.
2. **Всё остальное — 5-fold стратифицированная кросс-валидация на train**: подбор гиперпараметров, выбор лучшей модели,
   даже EDA. Если выбирать модель по test, оценка на test станет оптимистичной (мы подгоним выбор под шум).
3. **Стратификация** сохраняет долю дефолтов (22%) в каждом фолде.
4. В реальном банке разбиение было бы **по времени** (обучаемся на старых выдачах, проверяем на новых) — в этом
   датасете нет даты выдачи, поэтому случайное разбиение.

## 3. EDA и гипотезы

Скрипт `scripts/eda.py`, отчёт `reports/eda.md`. Хорошая практика — формулировать гипотезы до моделей и проверять их
простыми средствами: доля дефолтов по группам и **Information Value**.

### Information Value и WoE

Делим признак на бины. Для каждого бина:

```
WoE = ln( доля всех «хороших» в этом бине / доля всех «плохих» в этом бине )
IV  = Σ_бины (доля хороших − доля плохих) · WoE
```

WoE > 0 — бин надёжнее среднего, WoE < 0 — рискованнее. IV — насколько признак в целом разделяет классы:
< 0,02 бесполезен, 0,02–0,1 слабый, 0,1–0,3 средний, > 0,3 сильный (> 0,5 — подозрительно сильный, проверь утечку).

### Что получилось

| гипотеза | результат |
|---|---|
| H1. Просрочка в последнем месяце — главный сигнал | да: дефолт 14% при PAY_1 ≤ 0, 34% при 1, 70% при ≥ 2; IV = 0,88 |
| H2. Высокая утилизация лимита → выше риск | да, но **U-образно**: самые низкие доли дефолтов у средней утилизации, а клиенты с нулевой утилизацией рискованнее (часть из них — «спящие» карты) |
| H3. Кто гасит малую долю счёта, рискованнее | да: 29% в нижнем квинтиле против 16% в верхнем |
| H4. Больший лимит → ниже риск | да: 34% → 13% по квинтилям. Банк уже отобрал надёжных клиентов и дал им больше |
| H5. Демография — слабый сигнал | да: IV(AGE) = 0,02, IV(SEX) = 0,01. Возраст U-образный (молодые и пожилые рискованнее) |
| H6. Суммы счетов мультиколлинеарны | да: корреляции 0,80–0,95 → линейной модели лучше давать агрегаты |

## 4. Признаки

`src/credit_scoring/features.py::add_features`. Логика — «что сказал бы кредитный аналитик»:

| признак | формула | смысл |
|---|---|---|
| `util_i`, `util_mean`, `util_max`, `util_trend` | BILL_AMT_i / LIMIT_BAL | насколько клиент «выбрал» лимит и растёт ли долг |
| `pay_ratio_1`, `_mean`, `_min` | PAY_AMT_i / BILL_AMT_{i+1} | какую долю прошлого счёта погасил (платёж месяца i закрывает счёт месяца i+1) |
| `delay_max`, `delay_count`, `delay_recent2` | по PAY_i ≥ 1 | худшая просрочка, сколько месяцев с просрочкой, просрочки за 2 последних месяца |
| `months_since_delay` | индекс последней просрочки | давность: свежая просрочка хуже старой |
| `n_revolving`, `n_paid_full`, `n_no_usage` | число месяцев со статусом 0 / −1 / −2 | стиль пользования картой |
| `spend_mean_rel`, `pay_mean_rel` | траты и платежи / лимит | активность |

**Почему нет утечки.** Все признаки считаются по строке клиента, без статистик по выборке. Есть тест
`test_add_features_is_rowwise`: признаки первых 50 строк одинаковы, посчитаны они на всей таблице или только на этих
строках. Признаки, которые обучаются на данных (WoE), обучаются внутри фолда — для этого они встроены в пайплайн.

## 5. Модели

### Логистическая регрессия — бейзлайн

`P(default) = σ(w·x + b)`. Почему именно она бейзлайн в банке: интерпретируема (знак и величина коэффициента),
стабильна, её понимают регулятор и риск-менеджеры. Подготовка: суммы — `sign(x)·log(1+|x|)` (у них тяжёлые хвосты),
затем стандартизация; категории — one-hot.

**Бейзлайн на сырых признаках: AUC 0,734.** Та же модель с новыми признаками и one-hot статусами `PAY_1`, `PAY_2`:
**0,769**. Почему статусы в one-hot: зависимость нелинейная — значения −2, −1, 0 почти одинаково безопасны,
а 1 и 2 резко опаснее. Линейный коэффициент при числовом `PAY_1` это не выразит.

### WoE-скоркарта

Каждый признак заменяется на WoE своего бина → логистическая регрессия. Плюсы: монотонность внутри бина, устойчивость
к выбросам, нелинейность через биннинг, и главное — **модель превращается в балльную карту**:

```
score = offset + factor · ln(odds_good)          factor = PDO / ln 2,  offset = 600 − factor · ln 50
баллы бина = (offset − factor · b0) / n  −  factor · b_j · WoE_бина
```

PDO = 20 значит: +20 баллов — шансы «хороший : плохой» вдвое лучше. 600 баллов — шансы 50 : 1. Сумма баллов по
признакам — итоговый балл клиента. Такую карту можно распечатать и объяснить любому сотруднику.

**Контроль знаков.** Поскольку WoE растёт с надёжностью, а модель предсказывает дефолт, все коэффициенты должны быть
отрицательными. Положительный коэффициент — признак мультиколлинеарности: признак дублирует другой и «поправляет» его,
балльная карта становится бессмысленной (лучшая история — меньше баллов). Мы удаляем такие признаки по одному, начиная
с самого положительного (удалены `months_since_delay`, `util_1`, `n_paid_full`, `pay_ratio_mean`). Цена
интерпретируемости — AUC 0,752 против 0,769 у логрегрессии с one-hot.

### KNN

Оценка — доля дефолтов среди k ближайших клиентов (с весами по расстоянию). Требует масштабирования признаков,
медленный на предсказании, плохо работает в высокой размерности. k выбран по CV: k = 25 → 0,767, k = 200 → 0,778.
Большое k = сильное сглаживание: данные шумные.

### Случайный лес и градиентный бустинг

- **Random forest** — среднее многих глубоких деревьев на бутстрэп-выборках со случайным подмножеством признаков.
  Уменьшает дисперсию. AUC 0,778.
- **Градиентный бустинг** — деревья строятся последовательно, каждое следующее приближает антиградиент функции потерь
  (для logloss — остатки `y − p`). Уменьшает смещение. **LightGBM 0,784**, CatBoost 0,784, XGBoost 0,782.
- Отличия библиотек: LightGBM — гистограммы и рост дерева по листьям (leaf-wise), быстрый; CatBoost — симметричные
  деревья и ordered target statistics для категорий; XGBoost — рост по уровням, точный/гистограммный сплит.

Подбор LightGBM — случайный поиск по 16 конфигурациям на 5-fold CV. Лучшая: `num_leaves=7`, `learning_rate=0.02`,
`reg_lambda=20` — неглубокие деревья с сильной регуляризацией. Данных немного (24 000), сигнал простой.

## 6. Метрики — как их читать

| метрика | что значит | значение у LightGBM |
|---|---|---|
| ROC-AUC | вероятность, что случайный дефолтник получит PD выше случайного «хорошего» | 0,784 |
| Gini | 2·AUC − 1, банковское название того же | 0,568 |
| KS | максимальное расстояние между накопленными распределениями PD у «плохих» и «хороших» | 0,434 |
| PR-AUC | средняя точность; у случайной модели равна доле дефолтов (0,22) | 0,567 |
| Brier | средний квадрат ошибки вероятности; у константы 0,22 — 0,172 | 0,134 |

**Доверительный интервал** AUC — бутстрэп: 500 раз перевыбираем клиентов test с возвращением, считаем AUC, берём
2,5% и 97,5% перцентили. **Сравнение двух моделей** — парный бутстрэп: на одних и тех же перевыборках считаем разницу AUC.
Так учитывается, что модели ошибаются на одних и тех же трудных клиентах, и интервал разницы уже, чем у каждой модели.

**Калибровка.** Разбиваем клиентов на 10 групп по предсказанному PD и сравниваем средний PD с фактической долей
дефолтов. У всех моделей точки близко к диагонали (график в середине `model_comparison.png`). Если бы модель была
некалибрована (например, после балансировки классов), помогла бы калибровка Платта или изотоническая регрессия на
отдельной выборке.

## 7. Интерпретация: SHAP

SHAP раскладывает предсказание (в логитах) на вклады признаков: `logit(p) = base + Σ φ_j`. У деревьев есть точный
быстрый алгоритм TreeSHAP; LightGBM считает его сам: `booster.predict(X, pred_contrib=True)`.

Топ по среднему |SHAP|: `delay_recent2`, `PAY_1`, `delay_max`, `months_since_delay` — всё про свежие просрочки;
дальше утилизация и лимит. Это согласуется с IV и здравым смыслом — хороший признак отсутствия утечки.

## 8. Экономика: какой порог выбрать

Модель выдаёт PD, а решение «одобрить» — это порог. Его выбирают не по F1, а по деньгам. Условная модель:
одобренный «хороший» приносит +1 (процентный доход), одобренный дефолтник уносит −5 (потеря тела кредита).
Сортируем клиентов по PD и одобряем долю с наименьшим риском:

| модель | оптимальная доля одобрений | прибыль на заявителя | bad rate среди одобренных |
|---|---|---|---|
| бейзлайн | 62% | 0,165 | 12,2% |
| скоркарта | 62% | 0,179 | 11,9% |
| LightGBM | 52% | 0,239 | 9,0% |

Лучшая модель позволяет одобрять меньше, но заметно качественнее. Соотношение +1 / −5 — допущение; в реальном банке
его заменяют на процентную ставку, LGD (долю потерь при дефолте) и EAD (сумму под риском).

## 9. A/B-тест

Офлайн-метрики не гарантируют эффект в проде. Поэтому новую модель катят через A/B-тест.

**Дизайн:** клиентов случайно делим на группы A (старая модель) и B (новая). В обеих группах одобряем **одну и ту же
долю** заявок (70%) — иначе bad rate можно «улучшить» простым ужесточением политики. Метрика — доля дефолтов среди
одобренных. H0: доли равны. Тест — z-тест для двух пропорций:

```
z = (p_B − p_A) / sqrt( p̄(1 − p̄)(1/n_A + 1/n_B) ),   p̄ — общая доля
```

**Результат симуляции** на 6 000 клиентах test, 2 000 случайных разбиений:
- средний bad rate: A — 12,8%, B — 11,5%;
- **мощность** (доля экспериментов, где p < 0,05) — всего **24%**: эффект реален, но выборка мала;
- **A/A-тест** (обе группы — старая модель): 5,1% ложных срабатываний — тест ведёт себя как должен при α = 0,05;
- для мощности 80% нужно ≈ **9 100 одобренных клиентов в группе**:

```
n = ( z_{α/2} · sqrt(2 p̄(1−p̄)) + z_β · sqrt(p_A(1−p_A) + p_B(1−p_B)) )² / (p_A − p_B)²
```

Пример одного эксперимента в отчёте как раз показывает, что тест может «не увидеть» эффект: в нём B даже чуть хуже A.

**Особенности A/B в кредитовании** (частый вопрос на собеседовании):
- метка созревает месяцами — bad rate измеряют через 3–12 месяцев после выдачи (можно смотреть ранние индикаторы —
  просрочку 30+ дней на 3-м месяце);
- **reject inference**: на исторических данных мы видим исход только у одобренных старой моделью. Сравнивать модели на
  них — смещённо. Рандомизированный тест это смещение убирает;
- рандомизация по клиенту, а не по заявке;
- guardrail-метрики: доля одобрений, прибыль, одобрения по сегментам (модель не должна дискриминировать).

## 10. Что можно улучшить

- Разбиение по времени и мониторинг стабильности (PSI) — сделано в [credit-scoring-service](https://github.com/Killvarus/credit-scoring-service).
- Монотонные ограничения в LightGBM (`monotone_constraints`): PD не должен падать с ростом просрочки — модель станет
  объяснимее для регулятора.
- Калибровка и проверка стабильности Gini по подвыборкам (по возрасту, лимиту).
- Стекинг бустингов — даст +0,001–0,003, но усложнит модель.

## 11. Вопросы с собеседований

1. **Почему ROC-AUC, а не accuracy?** Классы несбалансированы (22%): константа «никто не дефолтит» даёт accuracy 78%.
   AUC не зависит от порога и баланса классов и меряет ранжирование.
2. **Что такое Gini и KS?** Gini = 2·AUC − 1. KS — максимум разницы накопленных распределений скоров плохих и хороших.
3. **Зачем WoE, если есть бустинг?** Интерпретируемость, монотонность, требования регулятора, устойчивость. Бустинг
   часто используют как challenger-модель или для поиска признаков для скоркарты.
4. **Почему коэффициент при WoE может стать положительным?** Мультиколлинеарность: признак коррелирует с другим и
   компенсирует его вклад. Лечится удалением признака или регуляризацией.
5. **Как выбрать порог?** По бизнес-метрике — ожидаемой прибыли или потерям, с учётом LGD, EAD и ставки, а не по F1.
6. **Модель хорошо работает на test, а в проде хуже. Почему?** Дрейф данных (PSI), сдвиг политики одобрения
   (модель училась на одобренных другой моделью — reject inference), утечка признаков, задержка метки.
7. **Как понять, что признак — утечка?** Подозрительно высокий IV / важность, признак известен только после события,
   резкий провал качества при разбиении по времени.
8. **Почему в A/B фиксируем долю одобрений?** Иначе разница в bad rate может объясняться не качеством ранжирования,
   а строгостью политики.
9. **Как посчитать размер выборки?** Через MDE, α и мощность (формула выше). Чем меньше эффект и базовая доля, тем
   больше выборка.
10. **Калибровка — зачем, если важно только ранжирование?** Для резервов и цены риска нужен сам PD; для лимитов —
    ожидаемые потери.
